# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A professional HR & administrative management web app for a mining company (TransWin Mining) operating 4 sites: **Ben Guerir, Louta, Bouchane, Mzinda**. Four roles: a **SuperAdmin** sees/manages everything across all sites; a **Responsable de site** is locked to exactly the site(s) assigned to them — one site for most responsables, but a responsable can be assigned to several sites at once (see below), both in the UI and (non-negotiably) in the backend; **`hse`** and **`responsable_hse`** are a separate, narrower pair of roles restricted to ONLY the HSE module (daily HSE reports) — see the dedicated section below — and never see anything else in the app, the mirror image of a plain `responsable` never seeing the HSE module at all.

Two separate apps in this repo, talking over a REST API:
- `backend/` — Laravel 11 API (PHP 8.2, MySQL, Sanctum token auth)
- `frontend/` — React 19 + TypeScript + Vite + Tailwind CSS v4

There is no root-level package manager — each app is built/run independently from its own directory.

## Architecture

### The one rule that matters: site-scoping is enforced server-side

A responsable must never see or write data from a site not assigned to them, even if the frontend is bypassed entirely. This is centralized in **`app/Http/Controllers/Concerns/InteractsWithSites.php`**, a trait used by every site-scoped controller:
- `resolveSiteId($request)` — for creates: a single-site responsable is auto-resolved onto their one site; a multi-site responsable or a superadmin must supply `site_id` explicitly, validated against `ensureSiteAccess`.
- `ensureSiteAccess($request, $siteId)` — aborts 403 unless the given site is one of the current user's assigned sites (`User::canAccessSite`).
- `scopeToSite($query, $request)` — for reads: restricts to `whereIn(site_id, user.assignedSiteIds())` for a responsable (every site assigned to them, aggregated at once — not just one), with an optional `?site_id=` narrowing it further to one of those sites (validated the same way); for a superadmin, the `?site_id=` filter is unrestricted (used for the global site switcher).

Never trust `site_id` from the request body/query for a responsable — always resolve/verify it via this trait. New site-scoped resources should follow the same pattern rather than inventing per-controller checks.

#### Multi-site responsables: assigned sites are usable simultaneously, not one-at-a-time

A responsable can be assigned to more than one site (`users` ↔ `sites` many-to-many via the `site_user` pivot, `User::sites()`/`assignedSiteIds()`). This used to work as a "switch your active site" model (one site forced at a time, `users.active_site_id`, a `PATCH /me/active-site` endpoint) — that was **replaced** (2026-09-17, migration `2026_09_17_000001_drop_active_site_id_from_users_table.php`) because the actual requirement is that a multi-site responsable's dashboards, KPIs, caisse and reports must **aggregate all of their assigned sites at once** (e.g. Fatima, assigned to Bouchane + Mzinda, must see both sites' combined personnel/attendance/cash numbers, never just one at a time and never Ben Guerir/Louta). `active_site_id` is gone entirely — there is no column, relation, or "current site" state left on `User` besides the computed `site` attribute (only non-null when the user has *exactly one* assigned site, used for the fixed "Site: X" label).

Concretely, a multi-site responsable now behaves exactly like a SuperAdmin, just restricted to a subset of sites instead of every site:
- **View filter**: `DashboardLayout.tsx` gives them the same `SiteSwitcher` pill/dropdown a SuperAdmin gets ("Tous" + one tab per site) via `useSiteFilter()`/`useSiteParams()` — the only difference is the site list passed in (`user.sites` instead of every site from `/sites`). "Tous" aggregates every assigned site; picking one narrows to it. No separate "ActiveSiteSwitcher" component exists any more — one `SiteSwitcher` serves both roles now.
- **Create forms**: any site-scoped create (cash expense, entry, manual exit, new employee) that used to show a Site `<select>` gated on `isSuperAdmin` now uses `useSelectableSites()` (`hooks/useReferenceData.ts`), which returns `{ sites, needsSiteSelect, isSuperAdmin }` — `sites` is every site for a SuperAdmin but only `user.sites` for a responsable (never leaking Ben Guerir/Louta into a Bouchane+Mzinda responsable's dropdown), and `needsSiteSelect` is true for a SuperAdmin or a responsable with more than one assigned site. A single-site responsable still sees no Site field at all — their site is auto-resolved server-side, exactly as before this feature.
- **Caisse**: `CashAccountController@show` and `DashboardController@index` return `sites: [{site_id, site_name, balance}]` (or `site_balances` on the dashboard) — every assigned site's own remaining spending limit, not a single `site_balance` number — so a multi-site responsable sees one KPI card per site. Declaring an expense requires picking which site it's for (`TransactionFormModal` in `CashPage.tsx`), and that expense only ever debits *that* site's own limit (see the Cash ledger section below) — declaring 1500 DH for Bouchane never touches Mzinda's limit.
- **Reports/exports**: `ReportController::exportSiteLabel()` uses the `?site_id=` filter if present (validated against the user's assigned sites), else the user's one site if they have exactly one, else `'mes-sites'` for a multi-site responsable with no filter applied (was `'tous-sites'`-equivalent behavior via `activeSite`, now gone).
- **`UsersPage.tsx`/`UserController`**: assigning a responsable to sites is just a multi-select of `site_ids` now — there's no separate "active site at first login" field to also set (`StoreUserRequest`/`UpdateUserRequest` dropped `active_site_id` entirely).

If you add another SuperAdmin-facing create form on a site-scoped resource, use `useSelectableSites()` the same way rather than gating on `isSuperAdmin` alone — a multi-site responsable needs the same explicit selector a SuperAdmin does, just scoped to fewer options.

`resolveSiteId()` throwing "Le site est obligatoire" means the frontend form for that create endpoint forgot to send `site_id` for a user who actually needs to supply one (a SuperAdmin, or now also a multi-site responsable) — a real bug hit on `EntryFormModal`/`ExitFormModal` (`MovementsPage.tsx`): both forms only had an "Établissement" free-text field (a different, unrelated concept — a physical building/facility name stored on the employee, not the `site_id` foreign key that drives all the site-scoping) and no `Site` selector at all. Both forms now show a required `Site` `<select>` (via `useSelectableSites()`) when `needsSiteSelect` is true, and only on create — same pattern already used in `CashPage.tsx`'s `TransactionFormModal`.

Manual-mode `ExitFormModal` (used when "L'employé n'existe pas dans la base") also gained a `Fonction` (`position_id`) select, matching `EntryFormModal` — the backend (`ExitController@store`) already accepted `position_id` for a manual exit, the frontend form just never exposed it, so there was no way to record what role a since-departed, never-entered employee actually held.

Role check (SuperAdmin-only routes) is a separate concern: `app/Http/Middleware/EnsureSuperAdmin.php`, aliased as `superadmin` middleware, wraps the relevant route group in `routes/api.php`.

Auth is Sanctum **personal access tokens** (`Authorization: Bearer ...`), not the SPA cookie flow — simpler given the frontend and backend are separate apps talking over a proxy. Token issued by `AuthController@login`, stored in `localStorage` on the frontend, attached by an axios interceptor (`frontend/src/api/client.ts`).

### Domain model

Core tables (see `backend/database/migrations/2025_01_01_*`): `sites`, `departments`, `positions` (all reference/lookup tables), `employees`, `attendances`, `leave_requests` + `leaves` + `leave_extensions`, `disciplinary_warnings`, `suspensions`, `assignments`, `entries`, `exits`, `cash_accounts` + `cash_transactions`, `audit_logs` (defined, not yet wired into every controller — see `App\Services\AuditLogger` for the write helper).

Notable relationship: **Employee → Site / Department / Position**, with a running **Assignment** history (`is_current` flag) that's created/updated automatically whenever an employee is hired (`EntryController`) or reassigned (`AssignmentController`), so the UI never asks the user to re-enter data that's already on file.

`App\Models\EmployeeExit` — note the name. The migration/table is `exits`, but `Exit` is a reserved word in PHP and can't be a class name, hence `EmployeeExit` with `protected $table = 'exits'`.

### Attendance: marking present must fully clear the old absence

`AttendanceController@store`/`@update` null out both `absence_cause` *and* `description` when `status` flips to `present` — not just the cause. Easy to miss because `updateOrCreate($keys, $data)`/`$model->update($data)` only touch the keys actually present in `$data`; a field silently omitted from the payload keeps its old DB value instead of being cleared, which is exactly what happened before this was fixed (a "Marquer présent" left the previous absence's description visible). If you ever add another status-dependent field here, remember `$data` needs the field explicitly, not just left out.

`AttendancePage.tsx`'s daily sheet also lets a responsable/SuperAdmin re-open the absence modal on an already-absent row (the small pencil icon next to "Marquer présent") to correct the cause/description in place — e.g. someone marked "non autorisée" who later brings a doctor's note should become "maladie" directly, not via mark-present-then-mark-absent-again. The modal pre-fills from the existing row (`isCorrection` in `AbsenceModal`) when doing this.

#### Cancelling a pointage deletes the record, it doesn't flip it

The red ✕ next to a row's actions (shown only when `attendance_id !== null`, i.e. something was actually keyed in) undoes a pointage entered on the wrong person. It calls `DELETE /attendance/{id}` — **removing** the row rather than marking the opposite — so the employee falls back to the day's *default* status (présent on a normal day, absent on a Sunday/holiday, see `daily()`). That's the real undo: before the mistake there was no record either. Don't "fix" this into a present↔absent toggle, and don't show the ✕ on a row that's still on the default — there's nothing to cancel there.

Cancelling an **STC** absence also has to undo the departure that absence triggered (`recordStcExit`): employee back to `actif` with `exit_date` cleared, the generated `exits` row deleted, the closed assignment reopened. Otherwise the single most damaging mistake in this module — STC on the wrong person — would be the one you can't take back. That revert logic lives in `App\Http\Controllers\Concerns\RevertsEmployeeDeparture` and is shared deliberately with `ExitController@destroy` (deleting a Sortie from Entrées/Sorties): both entry points must leave exactly the same state behind, so don't inline a second copy of it. The exit lookup matches on `reason = 'STC'` as well as employee+date, so cancelling a pointage can never delete a hand-entered Sortie that happens to share the same date.

On the frontend, a plain absent/present cancel fires immediately (it's reversible in one click — a confirmation on every correction is friction on the exact workflow this exists for), while an STC cancel goes through `ConfirmDialog` because it reaches beyond attendance. An STC cancel also invalidates the `employees` and `exits` query keys, since the employee comes back from "sorti" and their Sortie disappears.

The five `absence_cause` values are `maladie`, `autorisee`, `non_autorisee`, `conge`, `mise_a_pied`. `justifie` (added 2026-09-04) was later dropped and replaced by `mise_a_pied` (2026-09-08, migration `2026_09_08_000001_replace_justifie_with_mise_a_pied_in_attendances_absence_cause.php`) at the user's request — the five causes he wants tracked are exactly autorisée/non autorisée/maladie/congé/mise à pied, nothing else. `mise_a_pied` reuses the same badge label/color already defined for the *sanctions* module's `Suspension` type in `StatusBadge.tsx` — it's the same French term used for two different concepts (a disciplinary suspension record vs. an attendance day's absence cause), which is intentional, not a naming collision to "fix". It's an actual MySQL `enum` column, so changing the value set needs a migration that runs `ALTER TABLE attendances MODIFY absence_cause ENUM(...)` (widen first, backfill old values, then narrow — see the migration above) — you can't just edit the `Rule::in([...])` lists. Every place the cause list is duplicated must stay in sync when adding/removing one: `StoreAttendanceRequest`, both validation arrays in `AttendanceController` (`store`/`update` and `bulkStore`), `DashboardController`'s per-cause KPI counts (`attendance.absent_*`), the frontend `AbsenceCause` type and `DashboardData['attendance']`, `AttendancePage.tsx`'s `causeLabels` map and the `<select>` options, and `StatusBadge.tsx`'s `map`.

`AttendancePage.tsx`'s daily sheet (`AttendanceController@daily`) also accepts `?search=` (filters by employee name) and `?status=present|absent` (omit for "tous"), and always returns absent rows before present ones (secondary sort: full name) — the point is that on a busy site, the people who need action today shouldn't be buried under a long list of already-present employees. The page has its own "Export Excel" button next to the date picker, calling the existing `/reports/attendance/export` endpoint with `date_from=date_to=<selected date>` plus the same search/status filters — it doesn't duplicate `ReportController`'s export logic, just calls it with different params than the Rapports page does.

### Name search filters

`PersonnelPage.tsx` already had a `?search=` (by `full_name`) filter; the same pattern (a `SearchInput` bound to a `search` state var, included in the query params, `setPage(1)` on change) is now on every other module's list view too — `AttendancePage` (daily sheet), `LeavesPage` (both tabs: Demandes/Congés en cours), `MovementsPage` (both tabs: Entrées/Sorties), `SanctionsPage` (both tabs: Avertissements/Mises à pied), and `AssignmentsPage` (alongside its existing département/fonction filters). Server-side: `Entry`/`EmployeeExit` filter directly on their own `full_name` column (they don't always have an `employee_id`); every other module (`Attendance`, `LeaveRequest`, `Leave`, `DisciplinaryWarning`, `Suspension`, `Assignment`) filters via `whereHas('employee', fn ($q) => $q->where('full_name', 'like', "%{$search}%"))` since the name lives on the related `Employee`. If you add another site-scoped list page, add `search` the same way rather than leaving it out "for later" — every current list module has it now, so a new one without it would be the odd one out.

### Congés: a responsable can edit/delete their own site's demandes and congés, not just create them

Same "fix your own mistakes" pattern as assignments/entries/exits (see below) — `LeaveRequestController`/`LeaveController` already had `update`/`destroy` wired server-side (site-scoped via `ensureSiteAccess`), but `LeavesPage.tsx` only exposed create until 2026-09-08. Both tabs now show Pencil/Trash icons the same way `MovementsPage.tsx` does. Editing reuses the same `LeaveRequestFormModal`/`LeaveFormModal` used for create, keyed off an optional `request`/`leave` prop — the employee is fixed (shown read-only) on edit since `StoreLeaveRequestRequest`/`StoreLeaveTakenRequest` require `employee_id` on every write, so the edit mutation always resends the existing `employee_id` alongside the edited fields rather than letting the user reassign the employee via this form.

### A responsable can correct their own mistakes — except in the caisse

Everywhere except cash, a responsable has full CRUD on their own site's records, including `update`/`destroy` on `assignments`, `entries`, and `exits` (added after initially shipping those as create-only — a responsable needs to be able to fix a typo'd name/date/department without calling the SuperAdmin). Site-scoping (`ensureSiteAccess`) is still what gates it, same as everywhere else. Deleting an `exit` record reverts the linked employee back to `actif` and clears their `exit_date` rather than leaving them incorrectly flagged as gone — treat that as the expected "undo" behavior, not a bug. The **caisse is the one deliberate exception**: a responsable can only create (`store`) a declared expense; `update`/`destroy` on `cash-transactions` and everything on `cash-accounts` stay SuperAdmin-only (see the cash section below) — don't generalize the "let responsables fix their own mistakes" pattern to cash without being asked to.

### Cash: one real master caisse, plus a per-site spending LIMIT (not a second pot of money)

A `transfer` from admin to a site is **not a real money movement** — it never reduces the admin's own balance. It only raises a ceiling on what that site's responsable is allowed to spend. The only thing that ever actually spends real money is a declared `expense`, which is why it debits *both* ledgers at once. Concretely, with `cash_transactions.type` = `expense` | `entry` | `transfer`:

- The **master/common caisse** (`cash_accounts` is still a **singleton**, `CashAccount::singleton()` = `firstOrCreate([])`) is the admin's real balance — moved only by `entry` (+, an outside recharge) and `expense` (−, real money leaving on a site's purchase). A `transfer` never touches it. Example: admin has 12000 DH, transfers 2000 DH to Ben Guerir → admin is **still** 12000 DH; Ben Guerir then declares a 500 DH expense → admin becomes 11500 DH (not the transfer, the expense is what moved it).
- Each **site's remaining spending limit** — not a stored row (there's still no `cash_accounts` row per site), but **derived** from `cash_transactions.site_running_balance`: raised by `transfer` (admin extends the site's allowance) and consumed by `expense` (that site spending against it). Continuing the example: Ben Guerir's limit is 2000 DH after the transfer, then 1500 DH after its 500 DH expense. See `CashTransaction::currentSiteBalance()`, which uses the same `reorder()`-then-`latest()` trick as `CashAccount::currentBalance()` (see below).
- `site_id` is the site for `expense` (declaring site) and `transfer` (destination site); it's `null` for `entry` (site-less, funds the shared pot only, like the "Entree" rows in the reference `Book1.xlsx`).
- **Visibility**: a responsable can only create `type=expense` (auto-scoped to their own site, or explicitly picked among their own sites if they have more than one — see the multi-site responsables section above), can never create an `entry` or `transfer`, and never sees the master `running_balance`/`current_balance`/`initial_balance` anywhere. They *do* see `transfer` rows crediting their own site(s) (so their limit's history has a visible cause) and their own site(s)' `site_running_balance` — that's their own spending limit, they're allowed to see it. A SuperAdmin sees everything: the real master balance and every site's remaining limit (`summary.sites`) — there is deliberately no "grand total" KPI combining the two, since a site's limit isn't real money sitting anywhere, adding it to the master balance would double-count. Enforced server-side in `CashTransactionController` (`whereIn('type', ['expense','transfer'])` for a responsable's reads, `makeHidden('running_balance')` only — never `site_running_balance` — for a responsable), `CashAccountController@show` (role-shapes its response: SuperAdmin gets `{..., summary: {..., sites}}`, a responsable gets `{sites: [...]}` — one entry per site/pool assigned to them, see below), `DashboardController`, and `ReportController@cash`/`exportCash`. `routes/api.php`: `GET /cash-account` is available to any authenticated user (shaped by role in the controller); `PUT /cash-account` and `cash-transactions.{update,destroy}` stay SuperAdmin-only. The frontend (`CashPage.tsx`) mirrors this in what it renders (its table shows one "Reste global" column for a SuperAdmin — the real master balance — and one "Solde site" column for a responsable — their own limit; never both on the same table), but the backend restrictions are what actually matter.

#### Two or more sites sharing ONE responsable share ONE common caisse (`App\Services\SiteCashPool`)

This is deliberately **different** from "a responsable's dashboard aggregates their assigned sites" (that's about *reads* — see the multi-site responsables section above): here, two sites managed by the *same* responsable don't each get their own independent spending limit — they share a single pooled one. Example straight from the spec: Louta has its own 500 DH caisse, Ben Guerir has its own 500 DH caisse (each has a single-site responsable, so nothing changes for them — "la logique reste classique"), but Bouchane and Mzinda are both managed by the same responsable and share **one** 1000 DH caisse — a 200 DH purchase declared for Bouchane and a 300 DH purchase declared for Mzinda both come out of the *same* pool, leaving 500 DH, not two separate 300/700 balances. **This entire feature applies only to responsables — a SuperAdmin's access (every site, every caisse, every KPI, every report) is completely unaffected**, since pooling is derived only from responsable assignments (see below) and a SuperAdmin's unrestricted access never goes through it.

- **Derivation, not storage**: `SiteCashPool::forSite($siteId)` returns every site id sharing a pool with `$siteId` (including itself), computed fresh via a union-find over `site_user` rows belonging to `responsable`-role users only (a SuperAdmin has no `site_user` rows and never affects pooling). Two sites end up in the same pool **iff some responsable is assigned to both** — directly, or transitively through a chain of overlapping responsables. There is no `cash_pool_id` column anywhere; the pool is always re-derived from current `site_user` state, so reassigning a responsable's sites immediately reshapes which sites are pooled.
- **What actually changes**: `CashLedgerService::recalculate()` used to bucket `site_running_balance` by raw `site_id`; it now buckets by `poolKey()` (the lowest site id in the pool). A `transfer` "to Bouchane" and a `transfer` "to Mzinda" add to the *same* bucket when they're pooled; an `expense` declared against either debits that same shared bucket. `CashTransaction::currentSiteBalance($siteId)` now looks at the latest `transfer`/`expense` row across **every** site in `$siteId`'s pool (`whereIn('site_id', SiteCashPool::forSite($siteId))`), not just `$siteId` alone — the pool's most recent transaction from any of its sites carries the shared total.
- **Every place that lists per-site balances is grouped by pool, not by raw site**, via `SiteCashPool::groupedBalances(array $siteIds)` (one entry per pool, `site_name` already joined as `"Bouchane + Mzinda"`, `site_ids` listing every site in it): `CashLedgerService::summary()` (SuperAdmin's `summary.sites`), `CashAccountController@show` (a responsable's `sites` array), and `DashboardController`'s `cash.site_balances`. This is what stops a pooled responsable's dashboard from showing the same shared money twice under two different site names.
- **Per-site expense *attribution* is untouched** — every `cash_transactions` row still records its own specific `site_id` (which site the purchase was actually for), so "suivi précis des dépenses par site" (Rapports, the Caisse table's "Site" column) still breaks spending down by the exact site declared, even though the *balance* those expenses draw against is shared. Declaring an expense still requires the responsable to explicitly pick Bouchane or Mzinda (`TransactionFormModal` in `CashPage.tsx`, via `useSelectableSites()`) — pooling never removes that requirement, it only changes what the resulting balance check/display looks like.
- **Staleness trap**: `site_running_balance` is a cached/derived column, recomputed only when `CashLedgerService::recalculate()` runs. Since pooling depends on `site_user` (not on `cash_transactions`), *changing a responsable's site assignments* can reshape a pool without any cash transaction being written — so `UserController::store/update/destroy` explicitly calls `recalculate(CashAccount::singleton())` after every site-assignment change (`recalculateCashPools()`), and `DatabaseSeeder` does the same once after attaching the demo multi-site responsable (Bouchane/Mzinda's cash rows were seeded before that user existed, so they'd otherwise show stale unpooled balances until the next transaction). If you ever add another way to change a responsable's `sites()`, recalculate the singleton account the same way — don't assume the next unrelated cash write will happen to fix it.

### Cash ledger logic (`App\Services\CashLedgerService`)

`recalculate()` walks every transaction on the account in `(date, id)` order and maintains **two** independent running totals in the same pass, both via `bcadd`/`bcsub` on strings (never float): `running_balance` (the real master balance), moved only by `entry` (+) and `expense` (−); and `site_running_balance` (a *pool's* remaining limit, bucketed by `poolKey($transaction->site_id)` — see `SiteCashPool` above, not by raw `site_id`), moved only by `transfer` (+, raises the destination pool's limit) and `expense` (−, consumes the declaring pool's limit) — null for `entry` rows. **`expense` debits BOTH at once** — it's the only type that represents real money leaving the company, so it has to move the true balance *and* eat into the pool's allowance simultaneously; `transfer` never appears in the master ledger at all. Because a transaction can be edited or backdated, every write (`create`/`update`/`delete`) still recalculates the account's *entire* history, not just from the changed record forward.

**Two different, deliberately different, blocking rules**: an `entry` or `expense` is **never** blocked for exceeding the master balance — same "never block a real purchase" reasoning as before this feature existed, the master balance can go negative until the next recharge. A `transfer` is also never blocked (it isn't real money, just raising a limit — a superadmin can grant a site any limit regardless of the master's own balance). An `expense` **IS** blocked (422) if it would push its own site's `site_running_balance` (remaining limit) below zero (`CashTransactionController@store`, via `CashTransaction::currentSiteBalance()` + `bccomp`) — a site can only ever spend up to the limit the admin has granted it. Don't conflate these rules or "fix" one to match the other.

`CashAccount::currentBalance()` (and `CashTransaction::currentSiteBalance()`, which follows the same pattern) calls `->reorder()` before `->latest(...)` — the `transactions()` relation already has its own `orderBy('date')->orderBy('id')` baked in, and Eloquent's `orderBy`/`latest` calls **stack** rather than replace each other. Without `reorder()` first, the relation's ascending order wins and you silently get the *earliest* transaction's balance instead of the latest. This bit us once already; don't drop the `reorder()` call, and be wary of the same trap anywhere else that chains ordering onto a relation that predefines its own.

### Leave extensions never overwrite history

`Leave.end_date` is mutated on extension, but a `LeaveExtension` row is created first recording `previous_end_date` → `new_end_date` and the reason — the audit trail this produces is the point, not a byproduct. Follow the same pattern (append a history row, then update the denormalized "current" field) for any similar "this changes over time but we need the trail" feature.

### HSE module: two roles restricted to ONLY this module, nothing else

`hse` files the daily "RAPPORT JOURNALIER HSE" (réf. RJ-HSE-TRP-02 — the paper form this mirrors field for field, see `App\Models\HseReport`/`HseReportController`); `responsable_hse` reviews/controls every report on their assigned site(s); a SuperAdmin sees everything, unrestricted, same as always. This is a genuinely separate axis from the site-scoping rule above — it's not just "which sites can you see," it's "can you see this module at all":

- **Route-level, both directions, enforced server-side** (`routes/api.php`): every HSE route (`/hse-reports`) sits behind the `hse.access` middleware (`App\Http\Middleware\EnsureHseModuleAccess`, alias registered in `bootstrap/app.php`), which only lets `hse`, `responsable_hse`, or a SuperAdmin through — a plain `responsable` gets a 403. Every OTHER route in the app (`/dashboard`, `/employees`, `/attendance`, `/leaves`, `/cash-transactions`, `/reports/*`, `/sites`, `/departments`, `/positions`, `/holidays`, literally everything except `/login`/`/logout`/`/me`) sits behind `hse.block` (`App\Http\Middleware\BlockHseModuleRoles`), which throws a 403 for `hse`/`responsable_hse`. These two middlewares are the actual enforcement — the frontend nav/route guards below are UX only, never trust them alone.
- **Frontend mirrors this both ways**: `DashboardLayout.tsx`'s nav shows ONLY the "Rapports HSE" item for `hse`/`responsable_hse` (`isHseOnly` check) — every other nav item, including Dashboard, disappears; conversely "Rapports HSE" only appears for a SuperAdmin, never for a plain `responsable`. `App.tsx` backs this with route guards: `RequireFullAccess` redirects `hse`/`responsable_hse` away from every non-HSE route straight to `/hse`, and `RequireHseAccess` redirects a plain `responsable` away from `/hse` back to `/`.
- **Site-scoping still applies on top, unchanged**: `hse`/`responsable_hse` reuse the exact same `sites()` pivot, `assignedSiteIds()`, `InteractsWithSites` machinery as a `responsable` — a `responsable_hse` assigned to multiple sites (the seeded demo account is assigned to all 4) gets the same multi-site aggregation and `SiteSwitcher` filter as a multi-site `responsable` does elsewhere in the app (see the multi-site responsables section above) — there was no need to build a second site-scoping mechanism for this module.
- **One extra visibility rule on top of site-scoping**: an `hse` account only ever sees reports it created itself (`HseReportController@index` adds `where('created_by', $user->id)` for that role) — they file their own report, they don't audit their peers'. `responsable_hse` and SuperAdmin see every report across their site scope with no such restriction, since reviewing everyone's reports is the point of that role.
- **Who can write**: only `hse` (and a SuperAdmin, for flexibility) may `store` a report — `responsable_hse` is a reviewer, not an author, so `store` 403s for them. For `update`/`destroy`, the "fix your own mistakes" pattern from elsewhere in the app applies to `hse` (their own report only, `HseReportController::ensureCanEdit`), while `responsable_hse`/SuperAdmin — the controllers of this data — may correct or remove any report in their site scope, not just their own.
- **Site selection on create mirrors the multi-site pattern**: `HseReportFormModal` uses `useSelectableSites()` exactly like `CashPage`/`MovementsPage`/`PersonnelPage` do — a Site field appears only when the user has more than one assigned site, and only on create.
- Demo accounts (`DatabaseSeeder`): `hse.louta@transwin-mining.com` ("Bouskour Abderrahmane", single-site: Louta) and `responsable.hse@transwin-mining.com` ("Responsable HSE", assigned to all 4 sites) — the latter is deliberately multi-site to exercise the same aggregation as `fatima.multisite@transwin-mining.com`. ### Dark mode

Class-based, not OS-media-query-based, so the in-app toggle actually works regardless of system settings: `src/index.css` redefines the variant with `@custom-variant dark (&:where(.dark, .dark *));` (Tailwind v4 syntax), and `ThemeContext` (`src/contexts/ThemeContext.tsx`) toggles the `.dark` class on `<html>` plus persists the choice to `localStorage` (falling back to system preference only when nothing is stored yet). `index.html` has a tiny inline script that applies the stored/system theme to `<html>` before React mounts, so there's no flash-of-wrong-theme on load — if you ever touch that script, keep it in sync with `getInitialTheme()` in `ThemeContext.tsx`.

Every shared `components/ui/*` primitive and every page carries `dark:` variants (added in a bulk pass, then hand-verified). When adding new UI, follow the existing pairings rather than introducing new ones ad hoc: `bg-white` → `dark:bg-slate-900` (cards) or `dark:bg-slate-800` (inputs/hover surfaces), `border-slate-200` → `dark:border-slate-800`, `text-slate-900/800/700/600/500/400` → `dark:text-slate-100/200/300/400/400/500` respectively, colored badges/KPI icon chips use `dark:bg-{color}-500/15 dark:text-{color}-400` rather than the light `-100/-600` pair. One trap to know about: a class like `hover:text-slate-700` needs its dark override written as `dark:hover:text-slate-200` (hover-scoped) — writing plain `dark:text-slate-200` next to it looks similar but applies unconditionally in dark mode instead of only on hover, silently breaking the hover affordance. This exact mistake happened once already (from a careless bulk find/replace) and was fixed in the tab-underline components and the employee detail "Retour" link — don't reintroduce it.

### PWA: installable, works offline for real

This is a genuine installable PWA (desktop and mobile — Chrome/Edge show an install prompt, iOS supports Add to Home Screen), not just a bookmark shortcut, via `vite-plugin-pwa` (`vite.config.ts`) generating a real Workbox service worker (`generateSW` mode) plus a web manifest.

- **App shell**: fully precached (JS/CSS/HTML/icons/manifest), so the app loads and navigates even with zero connectivity.
- **Every `GET /api/*`**: `NetworkFirst` with a 4s timeout (one rule, `api-get-cache`) — prefers a live network answer and only falls back to the last cached one when the network genuinely fails (offline/slow). This used to be `StaleWhileRevalidate` for lists, which was a real bug: SWR returns the *cached* response immediately even when online, so a refetch right after a mutation (mark present/absent, edit a record...) showed the pre-mutation data — it looked like the action "did nothing" until a manual page reload picked up the revalidated cache. Don't reintroduce SWR for `/api/*` GETs for this reason; if a route ever needs instant-from-cache behavior, that has to be a deliberate, narrow exception, not the default.
- **Writes** (`POST`/`PUT`/`PATCH`/`DELETE` to `/api/*`): `NetworkOnly` + a `BackgroundSyncPlugin` per method — a mutation made while offline (declare a purchase, mark an absence, submit a leave request...) is queued in IndexedDB and replayed automatically once connectivity returns, up to 24h. This is the "enter things without a connection" requirement. Note the caveat: a queued write's `axios` promise never resolves (the request is intercepted before it reaches the network) — the UI's optimistic-looking success isn't guaranteed until the queued request actually replays, so don't build anything that assumes a mutation's response arrives immediately when offline.
- Navigation requests fall back to the cached `/index.html` shell, but `/api/*` is excluded from that fallback (`navigateFallbackDenylist`) so an API 401 while offline can't be masked by a stale "you're logged in" HTML response.
- `src/components/PwaStatus.tsx` registers the service worker (manually, via `virtual:pwa-register`) and owns the two pieces of UI a PWA needs: a persistent offline banner (`navigator.onLine` + `online`/`offline` listeners) and a brief "updating..." toast right before the page auto-reloads onto a new version. Mount it once near the app root (already done in `App.tsx`) — don't duplicate the registration elsewhere.

**Updates are automatic (`registerType: 'autoUpdate'`), not prompt-and-wait — this is deliberate, not the library default.** `'prompt'` (the more common choice) leaves a shipped fix sitting inert on every already-open tab and already-installed device until someone happens to notice a toast and click it; for an internal tool that's edited constantly, that's worse than the alternative of an occasional automatic reload. `onNeedRefresh` in `PwaStatus.tsx` calls `updateSW(true)` immediately (no button), and `onRegisteredSW` polls `registration.update()` every 30 minutes so a long-lived tab (people leave this open all day) still picks up a new version without needing to navigate. Verified end-to-end: built, registered the old service worker, rebuilt with a changed file, triggered `registration.update()` on the still-open tab, and it picked up and rendered the new build with zero manual action. Don't revert this to `'prompt'` on the assumption it's "less disruptive" — it directly caused a real bug report (a shipped fix not visible until a manual full reload).
- Icons live in `public/icons/`, generated from `src/assets/logo.jpg` by `scripts/generate-icons.mjs` (uses `sharp`, a devDependency) — standard (64/192/512) plus a separately-padded maskable 512 (OS icon shapes crop up to ~20% off each edge) plus an Apple touch icon. **Re-run `node scripts/generate-icons.mjs` whenever the logo changes** — the PNGs are checked in, not generated at build time.
- App name is "Solution Administrative" (manifest `name`/`short_name`, `index.html` `<title>`, and the Apple-specific meta tags) — keep these three in sync if it's renamed again.
- Test with `npm run build && npx vite preview` rather than `npm run dev` when checking real offline/install behavior — `devOptions.enabled: true` makes the SW active in dev too, but the production `generateSW` output is what actually ships.

### Every API response is `Cache-Control: no-store` — don't remove this

`app/Http/Middleware/PreventApiCaching.php` is appended to the whole `api` middleware group (`bootstrap/app.php`) and stamps `Cache-Control: no-store, no-cache, must-revalidate, private` on every `/api/*` response. This isn't optional hardening — without it, the **browser's own HTTP cache** (a layer beneath both axios and the service worker, keyed by URL only, not by the `Authorization` header) can serve one account's response to a *different* account that logs in afterward on the same browser. This was caught for real: `GET /api/me` came back with the previous session's role after switching accounts, which silently drove the whole UI's role-based rendering (nav items, site selector) off the wrong identity. `/api/me` also gets an explicit `NetworkOnly` rule in `vite.config.ts`'s `runtimeCaching`, registered *before* the general GET rule — Workbox's own Cache Storage ignores response `Cache-Control` headers for its own caching decision, so the backend header alone doesn't stop the service worker from caching identity too; both layers need the fix.

If you ever add a second caching layer (a CDN, a reverse proxy) in front of this API, make sure it also respects `no-store` — don't assume the two existing safeguards cover it.

### Excel export: every Rapports tab, plus Caisse, respects the same site-scoping as the screen

`ReportController` has an `export*` method next to each list method (`exportAttendance`/`exportLeaves`/`exportSanctions`/`exportMovements`/`exportCash`, routed at `/reports/{module}/export`), streaming an `.xlsx` via `App\Services\ExcelExportService` (a thin wrapper around `phpoffice/phpspreadsheet`, added for this — no other Excel package is installed). Each export method reuses the *exact same* query-building method as its list counterpart (`attendanceQuery()`, `leavesQuery()`, etc. — refactored out so the two can never drift), just swapping `paginate()` for `get()` since an export must contain every matching row, not one page. This means an export is scoped by `scopeToSite()` exactly like the on-screen table: a responsable always gets only their own site (their site name is baked into the exported filename, e.g. `pointage-louta.xlsx`) no matter what `?site_id=` they pass, a SuperAdmin with no site filter gets every site (`pointage-tous-sites.xlsx`), and a SuperAdmin with a site selected in the UI's site switcher gets only that site (`pointage-ben-guerir.xlsx`) — `exportSiteLabel()` derives this filename suffix from the same `site_id` query param `scopeToSite()` already trusts (or ignores, for a responsable). Don't build an export that bypasses `scopeToSite()`/`resolveSiteId()` "for simplicity" — it must go through the identical site-scoping path as everything else, verified live with a Louta responsable passing `?site_id=99` and still only getting Louta's rows.

Every export is styled like an actual table, not bare values: `ExcelExportService::stream()` bolds the header row with a sky-blue fill (`FF87CEEB`) and puts thin borders around every cell (header + data). It also takes an optional `?callable $highlightRow` — given a row's flattened array, return `true` to fill that row yellow (`FFFFFF00`). `exportCash()` is the one caller that passes this, flagging a row as an "Entrée" (recharge) or "Transfert" (rather than a "Dépense") so it visually stands out from a site's declared purchases at a glance; its last column is role-dependent, not the same for everyone — "Reste global (DH)" (the real master `running_balance`) for a SuperAdmin, "Solde site (DH)" (that site's remaining limit, `site_running_balance`) for a responsable — mirroring the same role split as the on-screen table (see the cash section above). No other export currently uses `$highlightRow`, but the mechanism is generic — pass a closure over whatever column distinguishes the row types you want to flag.

On the frontend, `ReportsPage.tsx`'s "Export Excel" button exports whichever tab is currently active, with the same site/date filters the table itself is using; `CashPage.tsx` has its own "Export Excel" button (next to "Nouvelle opération"/"Déclarer un achat") calling the same `/reports/cash/export` endpoint with its own filters, since Caisse is also a standalone page and not only a Rapports tab. Both go through `downloadFile()` (`api/client.ts`) — a small helper that requests with `responseType: 'blob'`, reads the real filename off the `Content-Disposition` header, and triggers a browser download via a temporary `<a download>` element. If you add another exportable list anywhere in the app, follow this exact three-part pattern (shared query builder on the controller + a `download*` frontend call + a button next to the corresponding table) rather than inventing a new export mechanism.
